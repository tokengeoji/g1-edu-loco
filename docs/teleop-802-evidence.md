# G1 FSM 802 보행 실험 기록 · 2026-11-23

11월 26일 운영자는 501에서 키보드 정면 출발을 확인했다. 802의 순수 전진·선회 계측, 2초 시험, 허리 옵션과 현재 조작법은 [FSM 802·501 정면 출발 비교](teleop-802-501-comparison.md)에 정리했다.

FSM 802에서 순수 전후진 ±0.15 m/s를 시험한 두 번의 기록에는 속도 요청의 성공 응답이 있지만 여섯 구간 모두 보행기가 정적 상태에 머물렀다. 운영자는 이후 +0.30 m/s에서 전진을 관찰했다. 다만 곧게 선 자세에서는 첫발 없이 기울기만 한 경우도 있었다. 현재 텔레옵은 옵션 없이 이 전진 속도를 요청한다. 802의 첫발 개시 조건과 −0.30 m/s 순수 후진의 재현성은 미확인이다.

### 2차 실기체 기록에서 비교할 구간

전방 변위는 각 구간의 시작 방위를 기준으로 한 기체 내부 오도메트리 추정치다. 각도는 구간마다 다리 12개 관절의 실측 최댓값−최솟값 중 가장 큰 값이다. 속도 벡터 순서는 전후(m/s), 좌우(m/s), 회전(rad/s)이다.

| 원본 구간 | 키와 요청 벡터 | 다리 각도 변화폭 | 전방 변위 |
| --- | --- | ---: | ---: |
| W1, W2 | `i` 전진 `(+0.15, 0, 0)` | 0.0049°, 0.0093° | 각 0.0 cm |
| W3 | `,` 후진 `(−0.15, 0, 0)` | 0.0117° | 0.0 cm |
| W4 | `o` 전진 우회전 `(+0.15, 0, −0.30)` | 24.69° | +8.4 cm |
| W6, W7 | `.` 후진 좌회전 `(−0.15, 0, +0.30)` | 7.69°, 4.12° | −6.5, −3.5 cm |
| W8–W11 | `m` 후진 우회전 `(−0.15, 0, −0.30)` | 11.36°, 10.57°, 4.49°, 2.99° | −8.3, −8.0, +1.8, −1.0 cm |

W1과 W4는 요청 직전 0.4초 동안 몸통 피치 중앙값이 각각 1.005°와 1.004°였다. W1의 다리 목표각 최대 변화폭은 0.89°였고, W4에서는 요청 26 ms 뒤에 첫 동적 상태 표본이 나타나고 목표각이 최대 49.94° 변했다. 따라서 이 두 구간에서는 요청 전달 이후에 생성된 관절 목표부터 차이가 있었다. 펌웨어가 어떤 조건으로 첫발을 결정했는지, 전류·온도 제한이 작동했는지, 발이 언제 바닥에서 떨어졌는지는 기록에 없다. 두 실험에는 횡속도 `vy ≠ 0` 요청도 없어 옆걸음 성능은 판정할 수 없다. [관절·응답 상세표](../src/g1_teleop/README.md#no-motion)

## 원본과 다음 기록을 읽는 방법

1. Notion의 **G1 EDU → 실험 데이터 → 2026-11-23 · FSM 802 보행**에서 01:39와 02:26 세션의 원본 ZIP을 찾는다. 2차의 `motion-window-summary.csv`에서 위 W 번호를 확인하고, `rpc.jsonl`에서 요청 ID와 응답을, `motors.jsonl`에서 같은 구간의 관절 목표와 실측을 대조한다. `sportmodestate.csv`는 정적·동적 상태, `odommodestate.csv`는 몸통 자세와 추정 위치를 담는다. 2차 원본에서 관절 CSV 세 개와 요청 구간 JSON을 다시 생성해 ZIP 안의 네 파일과 바이트 단위로 대조했다. [관절 CSV 재계산 코드와 시험별 검산 결과](experiments/2026-11-23-teleop/)
2. 새 세션은 입력 키(`i`, `,`, `m`), 코드 커밋, 속도 옵션, 시작 자세와 눈으로 본 첫발을 함께 기록한다. 아래 읽기 전용 기록기는 첫 속도 요청·첫 동적 상태·몸통 기울기·좌우 다리 반응을 같은 PC2 수신 시계에서 비교하는 데 쓴다.
3. `state/teleop.jsonl`에는 수신한 속도·정지 요청과 보행 상태 변화가, `state/samples.jsonl`에는 IMU 피치와 관절 실측이 있다. `state/manifest.json`에서 누락·폐기 표본을 확인한다. 이 기록기는 RPC 응답·발 접촉·오도메트리를 저장하지 않는다. 요청 수락이나 실제 보폭은 별도 관측이 필요하다. [기록기 사용법과 출력 항목](../src/g1stairs/monitoring/README.md)

**컨테이너 내부 · 30초 읽기 전용 기록**

```bash
g1 monitor record --with-teleop --nic eth0 --domain 0 --run "first-step-$(date +%Y%m%d-%H%M%S)" --seconds 30
```

## 같은 날의 카메라·계단 상태

05:18 UTC에 `rt/frontvideostream`을 기체가 광고한 DDS 메시지 형식으로 구독해 5.1초간 영상 패킷 148개(720p 72개, 360p 76개)를 받았다. 별도의 8초 관측에서 복호화한 640×360 컬러 영상 23장을 받았다. 설치 SDK의 고정 타입으로 검사했던 구독은 필드 구성이 달라 매칭되지 않았다. 같은 네트워크에서 머리 D435i의 ROS RGB·depth 토픽은 각각 발행자 0개·수신 0장이었다. USB 장치 목록에서는 D435i를 확인했다. 이 관측에서 전방 컬러의 물리 카메라와 머리 깊이 발행 실패 원인은 확정할 수 없다. 실험에 사용한 전방 영상 수신기와 디코더의 소스 사본은 이 분석 기록에 첨부했다. [실험용 전방 영상 수신 코드](experiments/2026-11-23-front-rgb/) · [카메라 수신 경로](camera-check.md) · [Unitree SDK에 포함된 고정 메시지](https://github.com/unitreerobotics/unitree_sdk2_python/blob/814556d15970dd2ecf1c9984e845ca02ab07e206/unitree_sdk2py/idl/unitree_go/msg/dds_/_Go2FrontVideoData_.py#L19-L27)
